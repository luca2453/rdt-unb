\begin{resumo}
	Este relatório apresenta a implementação e a avaliação de um protocolo de comunicação confiável baseado no mecanismo Stop-and-Wait (SAW), 
	utilizando o UDP como base. 
	O protocolo implementado permite a transferência de dados por segmentos, com confirmação de recebimento por mensagens ACK e retransmissão em caso de timeout. 
	Foram realizados testes com arquivos de diferentes tamanhos, analisando o tempo de ida e volta (Round-Trip Time, RTT) e a taxa de transferência (throughput). 
	Os resultados obtidos apresentaram RTT médio entre 11,51 e 11,95 ms e throughput medido entre 340,42 e 353,03 kbit/s, cerca de 99\,\% dos limites teóricos calculados. 
	Os testes foram realizados com um servidor desenvolvido pelos autores, pois o servidor disponibilizado para a atividade estava indisponível. 
	Os resultados evidenciam a influência do RTT no desempenho do protocolo.
\end{resumo}

\section{Introdução}

Com a expanção da internet para além dos PCs, se tornou necessário desenvolver aplicações com tempo de resposta mínimo.
Isso deve-se ao celular, hoje o principal meio de se conectar na internet, que exige protocolos rápidos - devido as exigências dos usuários -
e confiáveis - devido a perda de pacotes esperada das comunicações sem fio.

Dessa forma, um pode pensar que o protocolo TCP é ideal, porém, devido a perda de pacotes, o mecanismo de confirmar pacotes com ACK
pode cause retransimições excessivas, diminuindo a largura de banda da comunicação. Já o UDP também não é ideal, visto que não garante
a comunicação confiável, apesar de permitir uma largura de banda melhor.

Assim, este relatório é parte 1 de 3, visando criar um novo protocolo que mistura os pontos fortes do UDP e TCP afim de obter
o melhor dos dois mundos - confiável e rápido. Neste relatório 1, usando o UDP como base, é implementado uma forma básica de 
comunicação confiável chamada \textit{Stop-and-Wait (SAW)}.

No \textit{Stop-and-Wait}, o cliente pede um pacote de cada vez, espera e apenas solicita o próximo depois de recebido o pacote com sucesso.
Caso ocorra um timeout, o pacote é retransmitido até que se receba os dados solicitados.
O cliente, após receber cada pacote, confirma para o servidor enviando uma mensagem de ACK. Devido ao fato de que a maior parte do tempo é 
gasta esperando um pacote individuál, o SAW não possui largura de banda boa, mas é uma forma fácil de implmentar comunicação confiável.

Este relatório está dividido em 3 secções principais: na implementação é dito como foi feito o código que implementa o protocolo;
nos resultados, tem-se a verificação da confiábilidade e dados de throughput e RTT da transimição; e por último na análise, os dados
dos resultados são comentádos.

\section{Implementação}

O cliente foi desenvolvido em Python 3 apenas com bibliotecas nativas: \texttt{socket}
para a comunicação UDP, \texttt{argparse} para os parâmetros de linha de comando,
\texttt{hashlib} para o MD5 e \texttt{csv} para o registro das medições. Os parâmetros
\texttt{-{}-server}, \texttt{-{}-group} e \texttt{-{}-file} são obrigatórios; quando o
\texttt{-{}-group} não é informado, o próprio \texttt{argparse} interrompe o programa
antes que qualquer pacote seja enviado.

\section{Analise}

Um ponto imporante da técnica SAW é que seu throughput é limitado pelo round trip time (RTT). Isso é evidênciado nos gráficos obtidos.
Quando o RTT aumenta, imediatamente o throughput diminui. O inverso acontece quando o RTT diminui. Isso acontece, pois, para trasmitir
o próximo segmento, o cliente deve esperar o atual chegar. Dessa forma, o atraso para chegar o primeiro pacote, atrasa todos os pacotes
seguintes.

Além disso, o tamanho do segmento, que é relativamente pequeno, também não contribui. A quantidade de segmentos necessária para a transimição é
inversamente proporcional ao tamanho do segmento, assim, se o tamanho for pequeno, a quantidade de segmentos será grande, e o atraso devido a espera
do RTT também será grande. É possivel derivar uma fórmula para obter o throughput teórioco máximo desse método dado o RTT:

$$Throughput_{max} = (segment\_size × 8) / RTT_{medio}$$

Aplicando a fórmula aos RTTs médios medidos, obtém-se 512 $\times$ 8 / 11,95~ms
= 342,67~kbps para o \textit{small}, 355,79~kbps para o \textit{medium} e 352,84~kbps
para o \textit{large}. Os valores medidos foram 340,42, 353,03 e 350,10~kbps,
respectivamente, ou seja, cerca de 99\,\% do teórico em todos os casos
(Tabela~\ref{tab:throughput}). O teórico fica um pouco acima porque o RTT considera
apenas o tempo até a resposta do servidor, sem incluir o envio do ACK e o processamento
no cliente entre um segmento e o próximo. Como não houve nenhuma retransmissão, nenhum
\textit{timeout} afastou o medido do teórico. Além disso, a vazão quase não muda entre os
três arquivos, enquanto o tempo total cresce proporcionalmente ao número de segmentos
(24,6~s, 118,8~s e 239,6~s), o que confirma que o RTT é o fator limitante.

\section{Conclusão}

Assim, este relatório concluíu o objetivo de implmentar um protocolo de comunicação \textit{Stop-and-Wait}. Mostrou-se que ele consegue a trasmição confiável,
com vazão medida entre 340 e 353~kbps para um RTT médio de cerca de 12~ms.
Apesar disso, devido ao fato do servidor de testes provido pelo professor estar fora do ar durante o experimento, as conclusões feitas podem não condizer com as esperadas.
